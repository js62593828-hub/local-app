# N살림노트 원고 작업지시 (Claude Code용 · V1.1 · 2026-11-24)

> 이 폴더(docs/살림노트/)의 규칙 문서를 읽고 원고를 쓴다. 우선순위: 요청의 "이번 주 결정" > 원고지침_네이버_AB.md / 원고지침_네이버_C.md > 글뼈대규칙.md > 제목클릭규칙.md > 태그규칙.md > 스레드규칙.md. 서로 어긋나 보이면 쓰지 말고 멈추고 묻는다.
> 원고지침_네이버_C.md 사본은 AB와 똑같은 블록(피할 표현·카테고리·출처 캡처)을 "AB와 같다"로 줄여 두었다. 그 블록은 AB 파일을 본다.
> 분량·굵게·인용구·문단·사진·소제목·FAQ 같은 **기준 숫자는 이 파일에 적지 않는다.** 원고지침(AB·C)과 글뼈대규칙의 해당 블록을 읽어 따른다. 검사 도구 tools/salim_check.py 는 맨 위 STD·HOME 표 한 곳에 같은 숫자를 둔다.

## 1. 누가 쓰나
- 원고를 부르기 전에 글마다 `fact-checker` 에이전트(sonnet)로 사실 확인 메모 `pipeline/salim_drafts/<주>/_facts/<번호>_<키워드>.md` 를 먼저 만든다(검색 의도·공식 근거). 같은 주제 글은 메모를 함께 쓴다. 5장의 검색 작업은 이 단계에서 한다.
- 원고·제목은 `salim-writer` 에이전트가 쓴다. 요청에 메모 경로를 넣는다. 앞 글 내용은 요청에 길게 옮겨 적지 않는다(작가가 `tools/draft_digest.py` 로 확인). general-purpose 에이전트에게 "salim-writer 역할"을 시키지 않는다.
- 메인은 원고 파일을 통째로 읽지 않는다. 날짜별로 `python tools/salim_check.py --week <주>` 결과의 ✖ 만 본다. 같은 발행 날짜의 글은 동시에 부른다(최대 3개 동시). 날짜 하나가 끝나면 다음 날짜.
- 겹침은 미리 정한 값으로 막는다: 도입·뼈대·요약 이름·경험 장면은 요청이 글마다 정해 준다. 같은 날짜 글끼리 소제목 문구·경험 문장이 겹치는지는 tools/salim_check.py 가 본다.
- 메인 Claude Code는 입력 준비·검사·저장만 한다. 원고 문장을 직접 고쳐 쓰지 않는다(고칠 게 있으면 에이전트에게 다시 맡긴다).

## 2. 주 날짜를 받아 경로를 정한다
요청의 **주 날짜(그 주 월요일, 예 2026-11-30)** 를 `<주>`(2026-11-30 꼴), `<주8>`(20261130 꼴)로 쓴다. 아래 경로는 모두 이 날짜로 정하고 다른 주의 경로는 쓰지 않는다.
- 확정 목록: `Claude outputs/weekly_final_<주>.md` (글마다 확정 제목·예비 제목·검색 의도·본문 설계·제품 링크, 끝에 기존 글 목록 부록)
- 제품 자료·확정 링크: `pipeline/candidates_run/<주8>_naver_tips/` 의 `research/<상품id>.md`, `links.json`, `salim_slots.json`
- 저장 폴더: `pipeline/salim_drafts/<주>/`
- **확정 목록 파일 만드는 방법**: 앱 코드를 고치지 않고, 앱의 `/export-weekly-final` 을 불러서 만든다(화면의 [📤 주간 확정 목록 내보내기] 버튼은 config.py HIDDEN_FEATURES 로 숨겨져 있음). 대기열은 읽기만 한다. 같은 주 파일이 있으면 덮어쓰니 먼저 확인한다. 명령(주 날짜만 바꿈): `python -I -c "import sys; sys.path.insert(0, '.'); import app; print(app.app.test_client().post('/export-weekly-final', data={'week': '2026-11-30'}).status_code)"`

## 3. 이번 주 결정 — 요청이 준다
이 파일에는 특정 주의 값을 적지 않는다. 글마다 아래를 요청에 넣는다.
- 번호, 발행(날짜·시각), **유형**, 카테고리, 키워드, 뼈대·요약 이름, 도입 방식, 제품 수, 다음 글 예고 주제, 경험 장면, 저장 파일 이름, 앞 글 정보, **`홈판 글: 예/아니오`**.
- **제품 링크가 있는 글은 C 기준으로 쓰고 검사한다.** 확정 목록·대기열 유형이 A·B 라도 링크가 있으면 C 다(링크 없는 글은 대기열 값 A·B). 링크는 확정 링크(links.json)를 글자 하나 바꾸지 않고 `링크:` 줄에.
- 홈판 글인지는 사용자가 정해 지시문에 적는다(확정 목록·대기열에는 표시 칸이 없다). 홈판 글은 원고지침_네이버_AB.md [홈판 실험 글] 블록을 따르고, 원고 ⓪ 에 `홈판 글: 예/아니오` 줄을 반드시 쓴다(검사 도구가 이 줄을 읽는다).
- 링크 없는 글에는 링크·브랜드를 넣지 않는다. 확정 목록 "찾을 제품 조건"은 링크가 없으면 무시한다.
- 이어지는 주제의 기존 글은 내부 링크 후보로(확정 목록 부록).
- 경험 장면은 글마다 미리 정해 요청에 넣는다(원고지침 [운영자 경험] 금지 규칙 그대로).

## 4. 제목 — 확정 제목 그대로
- 확정 목록의 확정 제목을 **글자 하나 바꾸지 않고 그대로** 쓴다. 키워드 위치·길이 같은 제목 규칙은 원고지침 3단계와 제목클릭규칙을 따른다.
- 더 나은 안이 있으면 원고 밖(⓪ 구역, 코드 블록 바깥)에 `제목 대안(메모): … / 이유: …` 1개만 적는다. 원고에는 쓰지 않는다.
- 제목 속 숫자는 근거를 확인하고, 없으면 제목을 바꾸지 말고 점검 줄에 "제목 숫자 근거 없음"이라고 적는다.
- 출력: 원고 앞 `확정 제목에서 바뀜: 아니오`.

## 5. 검색 의도 — 확실하게 담기
- 글마다 키워드로 웹 검색해 상위 글 제목·연관검색어를 직접 본다(네이버를 못 보면 구글, "네이버 결과 미확인"이라고 적음).
- 원고 앞 "의도:" 한 줄 = 이 키워드로 검색하는 사람이 가장 알고 싶은 것 한 문장. 확정 목록 검색 의도와 다르면 고친 의도를 쓰고 이유를 한 줄.
- 도입 3~4문장에 그 답을 주고, 요약 블록 3줄이 그 답을 정리하고, 소제목들이 그 질문을 순서대로 풀어야 한다. 상위 글이 공통으로 빠뜨린 것 1개 이상을 섹션으로 채운다.
- 의도와 상관없는 섹션(분량 채우기)은 넣지 않는다.

## 6. 표지 글자 — 자연스럽게
표지 1줄·2줄은 두 줄을 이어 소리 내어 읽었을 때 **이웃에게 하는 말 한마디처럼** 들려야 한다.
- 각 줄은 말로 끝나는 짧은 문장이거나, 그대로 말해도 어색하지 않은 말 덩어리. 명사만 늘어놓지 않는다.
- [대괄호]는 줄마다 1개, 강조할 낱말 하나에만. 대괄호를 빼고 읽어도 문장이 된다.
- 쓰지 않는다: 추상어 "손해·헛수고·낭패", 잘린 말("~어떤 걸로", "~말고"), 한 줄에 대괄호 2개, 줄 길이는 원고지침 값 초과, 숫자 둘 이상 나열.
- 지난 글에서 어색했던 예 → 고친 방향
  - "요금 [3배] 차이 이유" → "요금이 [3배]까지 나요"
  - "끓는 물 부으면 [손해]" → "끓는 물 부으면 [다시 굳어요]"
  - "난방텐트 [어떤 걸로] / [침대냐 바닥이냐]" → "난방텐트 [어디에] 칠까요 / 침대냐 [바닥]이냐부터"
  - "주방엔 [연기감지기] 말고 / 방마다 [다르게]" → "주방엔 [열감지기]가 맞아요 / 방마다 [종류]가 달라요"
  - "우리집 소화기 [작동되는 것 맞겠지]"(너무 김) → "우리 집 소화기 [괜찮을까]"
- 잘 된 예: "니트가 왜 [줄어들까]? / [30도] 물로 누르듯 빨기", "외풍 어디서 [새나요] / [휴지 한 장]이면 찾아요", "비비면 [줄어들어요] / [눌러서] 빨면 돼요"
- 표지 1줄은 제목과 같은 장치·결과 말을 쓰고, 표지 장면과 같은 이야기를 한다.
- 원고 파일 끝 점검 줄에 "표지 글자 소리 내어 읽기 ✔"를 넣는다.

## 7. 제품 자료 (C 글)
- research/<상품id>.md 에서 쓰는 것: 상품명, "## 사양 (페이지에 있는 것만)"의 값, 상품정보 제공고시 값. "없음"인 칸은 쓰지 않는다(필요하면 "상세 페이지에서 확인해 보세요").
- 쓰지 않는 것: 판매가·할인 전 가격·평점·리뷰 수·별점 분포(가격·숫자 금지), 쇼핑몰 주소.
- "## 후기 요약"은 **그 제품군과 맞는 주제일 때만** 요약해서 쓴다. 주제가 제품과 안 맞으면(수집 오류) 후기 요약 전체를 쓰지 않고 원고 앞 ⚠ 줄에 적는다.
- 자료가 빈약하면(사양이 거의 "없음") 지어내지 말고, 고르는 기준·사기 전에 확인할 것을 공식 근거로 채우고 ⚠ 줄에 "제품 사양 자료 부족"을 적는다.

- 폴더: `pipeline/salim_drafts/<주>/`
- 파일 이름: `NN_MMDD_HHMM_유형_키워드.md` (예: `01_1130_0700_A_배추보관.md`, 유형은 위 3장 기준으로 정한 값)
- 파일 안 순서(원고지침 출력 형식 그대로, 코드 블록은 ``` 로):

  2. ② 본문 코드 블록(`[플랫폼:네이버]` 첫 줄, `제목:` 줄)
  3. ③ 메타데이터 코드 블록
  4. ④ 링크 위치·내부 링크 / ④-1 경험 문장 확인 / ⑤ 사진 팁(선택) / ⑥ 출처(확인용)
  5. [스레드] 블록
  6. 점검 줄: 키워드 글자 그대로·제목 앞쪽 / 근거 문장 수 / 인용구·굵게 개수 / 경험 문장 수·금지어 0개 / 마무리 인사 3요소 / 뼈대 / FAQ n쌍 / 분량(공백 제외 n자) / 태그 n개 / 피할 표현 0개 / 표지 글자 소리 내어 읽기 ✔ / (C) 자료에 없는 제품·스펙 0개·써 본 척 0개·가격 0개
- 앱 데이터(content_queue*.json·articles*.json)에는 넣지 않는다. 사용자가 편집기에 붙여 넣는다.
- 검사: `python tools/salim_check.py --week <주>`

## 9. 보완 규칙 — 모든 글에 적용
1. **검색 결과 요약만 보고 쓴 근거는 본문에 넣지 않는다.** 페이지를 실제로 열어 문장을 확인한 출처만 "○○에 따르면"으로 쓴다. 못 열었으면 그 문장을 빼거나 이미 확인한 다른 출처로 바꾼다.
2. **근거는 그 글의 장면과 직접 이어지는 것만.** 다른 장소·다른 물건 이야기를 끌어와 기준처럼 쓰지 않는다.
3. **C 결정형의 제목·도입·요약은 제품 자료로 확인된 사실만 약속한다.** 자료에 없는 효과(미끄럼 방지·안전·보온 시간 등)를 제목이나 표지에서 약속하지 않는다. 안전과 관련된 효과는 자료나 공식 근거가 없으면 "확인할 점"으로만 쓴다.
4. **숫자 도입은 그 숫자가 제목이 약속한 답과 바로 이어질 때만.** 이어지지 않으면 장면이나 오해 도입으로 바꾸고 원고 앞에 이유를 한 줄 적는다(요청의 도입 방식보다 이 규칙이 우선).
5. 제품 사양 자료가 거의 없는 C 글은 원고 앞 ⚠ 줄과 함께, 보고에도 "제품 자료 부족"을 따로 적는다(사용자가 제품을 바꿀지 판단).
